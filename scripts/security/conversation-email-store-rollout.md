## Recovery semantics

The first import obtains a history baseline before listing messages. Expired-history recovery obtains a replacement baseline and atomically clears stored mailbox messages and resets all requested imports. This intentionally exposes a temporary partial/empty store while replaying ranges, rather than retaining messages that may have been deleted at the provider. The commit uses a valid mailbox lease; expired workers cannot reset jobs or commit old pages.

Invalid OAuth refresh grants pause jobs for reconnect; temporary token errors retry. Updating the stored refresh credential resumes paused jobs, preserves checkpoints, and invalidates active leases. Workers receive a 20-second provider-work deadline (bounded by the scheduler's remaining 60-second conversation budget), reserving three seconds for commits. Unfinished message IDs are stored in the checkpoint; history advances only after the whole page is handled.

The scheduler shares a 150-second work budget across conversation work and legacy note capture, leaving 30 seconds below its checked-in HTTP timeout for cleanup/response. Legacy mailbox batches receive at most 30 seconds, reduced to the remaining shared budget. Their token/list/message calls share an absolute provider deadline with three seconds reserved for cleanup; expiry retains the cursor. Mailboxes not started before the remaining budget falls to five seconds are counted as `deferred`, not failed. These bounds cover provider requests/retries and admission checks, not unbounded database latency: membership queries, queue operations, note transactions, commits, and cleanup can still overrun. This is not a hard end-to-end timeout guarantee.

`sync.importComplete` reports range import completion separately from `sync.freshness` (`pending`, `current`, `stale`) and `sync.lastSyncedAt`. Only a completed history scan marks freshness; initial/recovery baselines do not. Freshness becomes stale after 15 minutes, allowing three cycles of the checked-in five-minute scheduler. Delay/reconnect errors remain higher-priority UI states. Wall-clock lease validation rejects commits even if the transaction began before expiry. A second validation after writes rolls back the complete message/checkpoint/freshness batch if the lease expires during those writes.

Repository targeting review: the primary service client uses `NEXT_PUBLIC_SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`; CRM uses `CRM_SUPABASE_URL`/`CRM_SUPABASE_SERVICE_ROLE_KEY`. Only when `VERCEL_ENV=production`, the production build guard requires both aliases to target the configured production project and keys to match. Local-config builds do not exercise that guard. The checked-in scheduler dispatches to `app.headlinerma.com/api/internal/gmail-sync` every five minutes with a 180-second HTTP timeout, versus the route's 300-second platform maximum and 150-second application work budget. None of these repository declarations verifies the deployed configuration; total runtime including database delays and actual scheduler settings remain rollout gates.

Old code can use the replaced claim function's compatible signature, but does not provide new fencing/backoff guarantees. Verify legacy operation before resuming. Do not drop tables, credentials triggers, or RPCs while any deployed code or in-flight worker depends on them. Destructive database rollback requires a separate reviewed data-preservation plan.

## Database-delay and concurrency coverage

Synthetic execution tests inject delays at claim, permission, lead matching, conversation commit, and cleanup boundaries. Expired admission stops provider work; rejected commits report delay rather than completion; cleanup is awaited and remains lease-token fenced. Real disposable PostgreSQL sessions hold mailbox/job locks beyond lease expiry, and a slow message trigger exhausts a lease during writes to verify atomic rollback. Overlapping range checkpoints are interleaved with partial history and reconnect: outstanding IDs survive, partial work does not publish freshness/completion, and old tokens cannot advance history. Concurrent scheduler reservations are disjoint. These are deterministic local regressions, not production load tests or a guarantee against unbounded database stalls.
