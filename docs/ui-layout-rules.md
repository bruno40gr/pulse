# Shared UI layout rules

## Flat surfaces

- Use `spacing.lg` for peer-card gutters in the lead detail surface: summary cards, vertical card stacks, column separation and the content inset below the toolbar. Align Notes and summary-card top edges; do not add a Notes-only inset or extra column-side padding. Internal field spacing is independent of card gutters.

- Use `DenseSectionPanel` for titled groups with header actions. It defaults to flat, an 8px radius, 18px padding and no shadow. Use its `actions` slot for card-level actions.
- Use `SurfacePanel appearance="flat" tone="muted"` for quiet contact/lesson summaries. Muted flat surfaces have no border or shadow.
- `SurfacePanel` retains its raised default for existing unrelated screens; use `appearance="raised"` explicitly when elevation is meaningful. Do not add shadow overrides to profile cards.
- Lead and contact detail cards use the shared default border (`colors.border`); do not override contact cards with `colors.borderLight`. Keep the light token for structural dividers. Both communication rows use `SlidePanelActionBar`: white background, light bottom divider, matching responsive padding and wrapping. Preserve per-view routing, permission, account-holder fallback and disabled-state rules; unavailable actions may legitimately look different.
- Ordinary form sections use a heading and spacing, not another box. Box a repeatable entity (student, family member, lesson) or independently actionable content. Do not box a dropdown alone or nest cards for each field.
- Add-lead students are an explicit exception to entity boxing: keep the outer Students section, but render Student 1, Student 2, etc. as borderless fieldsets with legends and spacing. Do not put a box around each student.

## Fields and dropdowns

- Communication actions use shared `Button` variants: primary Call, secondary SMS/email, ghost copy. Enabled, disabled, and loading presentation belongs to the shared library, never per-panel inline styles or CSS. Data and routing determine availability only; the same action in the same state must look identical in lead and contact panels.

- Maximum **two editable controls per row**, including dropdowns. Three or more dropdowns are never a form row.
- Use `FieldGrid`: one column by default, two only when the grid's actual container is at least 540px wide. With an 18px gap this leaves at least 261px per control. This is container-based: a narrow rail on a desktop stays one column.
- Pair only short, related fields (first/last name, email/phone, date/interval). Long options, multi-selects, conditional controls, descriptions and address/search fields get a full-width row (`FieldGrid columns={1}` or a separate grid). Do not pair unrelated controls merely to fill a gap.
- A repeatable person's header contains their name/number and removal action. Controls go below, not in the header beside trash. Do not squeeze name, age, program and trash into one row.
- Shared `Input`/`Select` have 42px minimum height. `Select` reserves space for a decorative caret inset 12px from the right, retaining native interaction and native arrows in forced colors. Compact table/status controls may explicitly opt into smaller dimensions; normal form fields may not.
- Associate every editable label with its control. Shared controls generate an ID if needed and link helper/error text. Keep keyboard focus visible. Read-only `FieldLabel`/`DetailField` are not editable form labels.
- Required fields start neutral. In Add lead, use neutral gray helper text while filling out the form; reserve red errors and invalid semantics for an attempted save. Focusing or leaving fields must not trigger missing-value warnings. Clear errors when corrected and reset submitted state for a fresh form. Required indicators and neutral hints are allowed before interaction. Keep submission available to explain missing values, guard requests with validation, and disable only while saving. Add lead requires a contact name and a valid email address. Phone does not substitute for email; phone remains optional.

## Heading hierarchy

- Inside-card titles use `SectionTitle variant="card"`: 18px (`sizeLg`), bold (`weightBold`), with header spacing owned by the card. `DenseSectionPanel` applies this automatically to string titles; custom title nodes must use the same variant. Apply consistently across enrollment, lead and contact surfaces, including Notes and Follow-up. Keep semantic h2/h3/h4 levels unchanged; do not globally restyle h3 or add per-screen size/weight overrides.

- Blocked Add-lead saves focus and scroll to the top error summary, retain inline field errors, and repeat the failure message beside the bottom save action. Require email and validate its basic format even when phone is supplied. Enforce this for manual intake on the server without changing public website phone-only capture. This is syntax checking, not address verification.

- **h1:** page title, once per page.
- **h2:** page's main sections, or a drawer/dialog title (`SlidePanelHeader`). A drawer does not get another h1 just because it overlays the page.
- **h3:** sections beneath that h2, e.g. Contact details, Request details, Follow-up, Student 1 in an enrollment step.
- **h4:** a nested entity beneath an h3, e.g. Family member 1 inside Family members. If a lower heading is needed, use it rather than skipping levels to obtain a smaller font.
- `SectionTitle as="h3"` chooses semantics explicitly. `DenseSectionPanel` string titles default to h3 and accept `headingLevel`. Custom title nodes must select their own heading level. Visual scale is separate from hierarchy.
- Card titles use `SectionTitle variant="card"` with the shared `typography.h2` role and `spacing.md` bottom margin. Read-only metadata uses `FieldLabel` and `FieldValue` (or `DetailField`), shared by Leads and Account. Do not reproduce their styles in page CSS or add page-scoped typography overrides. Editable labels continue to belong to the shared form controls.
- A label, field value, metric, name chip or action is not a heading just because it is bold.
- Add lead is a form surface with peer **h2** sections: Contact details, Students, and Attribution (or Request details for service inquiries). Do not mechanically demote all drawer sections to h3 because the drawer title is h2. The form's information architecture determines these peer sections; student fieldsets remain subordinate. Attribution uses the shared Disclosure and defaults closed.
- Add lead's surface title is **h1**, configured through `SlidePanelHeader headingLevel="h1"`; existing detail panels retain h2 by default. Header sizing belongs to the shared header: 88px minimum on desktop and 68px on mobile, with 20px/10px vertical padding matching account workspaces. Preserve close-control hit targets and let long titles/subtitles grow naturally.

## Adoption and scope

Applied to enrollment student/review surfaces and responsive field grids; lead detail/family editors; contact profile/edit cards; and add/edit-lead section grouping. Existing scheduling/lesson-specific controls retain domain behavior and their selected-state styling. Notes retain bounded scrolling, and communication controls remain in their surface header.

These are presentation changes, not identity, consent, booking, payment or messaging-contract changes. Shared form accessibility and caret improvements intentionally apply to other consumers of those primitives. Browser review at narrow and wide panel widths is required before calling the visual pass complete.

## Add-lead information architecture

Do not replace the Students section with a family-count stepper or a single generic request form. Lesson/tour inquiries use a Students section with an Add student header action and numbered student fieldsets. Contact details owns contact name and birthday. When Classes are for myself is checked, hide the student name and birthday controls and use the current contact values; do not show read-only duplicates. Unchecking reveals the separate student's name/birthday and preserves previously entered draft values. Lesson-interest controls (service, program, experience, available days and preferred times) remain visible in both states. Service and program belong to each student, not to the contact. The screenshot's grouping is preserved while field rows still cap at two. Concrete cards determine the interested-student count.

Component/style migrations must preserve conditional visibility, default state, draft retention and submitted values. Record those behaviors in regression tests before replacing form structure. A rendering test alone is not evidence of behavioral parity. Do not invent missing historical conditions when they cannot be recovered; identify that gap explicitly.

Student details are saved as inquiry payload (`student_requests`), not canonical identities or enrollment. First-student summary fields and existing family/sibling projections remain populated for current lead readers. The current legacy edit/detail forms do not yet provide a complete per-student birthday/service editor; do not claim that migration is complete.
## Account task workspaces

- Account-manager profiles keep the holder as the navigation scope: header subtitle “Account manager”, Contact details with Name/Email/Phone, and a Family card with each child’s birthday and subscription count. Add a child belongs in the Family card header. Do not show an Account managers card for the manager or child-profile shortcut buttons inside Family.
- In the account-manager view, group subscriptions under each student’s name heading. Upcoming lessons combine all children chronologically; makeups stack all children without child selectors. Tasks retain and return to the originating manager context. Notes at this level use the account ID, not child IDs; never silently merge existing student notes into the account feed.

- Full-view account tasks use `AccountWorkspace`: an icon-only back chevron, the originating profile avatar and name, and the student/family profile subtitle, followed by the task H1. Reuse `ProfileIdentity` from `SlidePanelHeader`, including avatar dimensions and typography; do not substitute a blue text-link name or add a duplicate profile header.
- Profile headers use a 24px desktop / 16px mobile inset. Do not reserve an empty Back slot: only a real Back control adds its 44px width and 8px gap before the identity. The identity transitions between positions over 260ms; task content enters independently. Both respect reduced motion.
- The shell owns the 1440px content maximum width, header spacing, content gap and heading focus on entry. Hosts provide the existing responsive outer gutter; individual forms must not add another page inset or task-specific centered width.
- Full workspaces use an 88px desktop / 68px mobile minimum profile header, preserving the panel’s horizontal identity offsets. Body inset totals 40px on desktop with 32px top spacing; task H1s are 24px semibold (22px on mobile), with 24px before task content. Calendar columns have a 28px gutter.
- `SlidePanelHeader` matches the workspace header’s 88px desktop / 68px mobile minimum height. Use 20px desktop / 10px mobile vertical padding in the panel: the mobile Close target is 48px versus the workspace’s 44px Back target, so 2px less padding per side keeps the rendered heights and identity offsets equal. Preserve matching vertical as well as horizontal profile identity offsets when moving between panel and workspace; headers with extra badges or wrapped content may grow naturally.
- Calendar browsing uses a compact Teachers menu populated from scoped lessons; hide it when fewer than two teachers are relevant. Booking calendars have no teacher checkbox strip: enrollment keeps a teacher preference per lesson in its details, makeup retains its same/any preference, and time-slot selection still resolves the available teacher. These are preview data sources, not live teacher integrations.
- Management forms (including subscription, invoice and statement), calendar browsing, makeup booking and lesson moves share this shell. Callers retain responsibility for identity scope, return destination, draft state and mutations. V2 must suppress its profile shell header for these focused tasks.

## Billing preview

- Present outstanding balance as a section-level summary, not an inert card. Show a fully overdue balance once as $X overdue in red. For a mixed balance, show $X outstanding with overdue and upcoming amounts underneath. Use due [date] for invoice dates, not Next payment unless an actual collection is scheduled.
- Invoice cards keep status beside the title, amount beside due date on the left, and actions on the right. Pay is red and primary; omit it for paid/draft invoices. View invoice opens the itemized invoice; card Pay opens payer/card confirmation directly. Download PDF is available only inside invoice details, not on invoice cards, and downloads without navigating. Do not give View and Pay identical destinations.
- Invoice details reuse the uploaded company logo and show billed-to, issue/due dates, line-item quantities/unit prices/amounts, total, paid and amount due. Use the invoice name as the screen title next to the Back chevron. Place right-aligned Download PDF followed by primary Pay below the invoice preview, not in its header. Keep actions in normal document flow—no sticky, fixed or floating footer. Invoice card and detail action pairs use equal-width, equal-height medium buttons using the shared Button md sizing, without custom minimum heights. Payment opens a compact confirmation dialog, never a duplicate invoice workspace; cancel returns to the originating invoice or invoice list.
- Keep admin payment confirmation selectors labeled Paying as and [name]’s payment method. Cards are scoped to the selected payer. Payments record paid-by identity separately from billed-to identity, including Pay all and exports; never rewrite invoice responsibility or subscription payers when settling an invoice. Staff manage future subscription payer changes directly; add no invitation, acceptance, transfer-request or approval dependencies. The existing parent preview remains read-only and exposes only its original invoice/card scope.
- Put Create statement and Issue invoice in the Billing actions overflow menu, not standalone toolbar buttons. Keep Pay all prominent.
- Pay all appears for multiple open invoices in the current billing scope, excludes paid/draft invoices, lists the selected invoices and total, and requires a payer-owned saved card plus explicit confirmation. Apply the preview batch atomically. Preview payments are local state only; no card is charged.

## Student communication preview

- Do not append the account-manager name beside profile communication actions. Inside messaging, show a single Messaging [resolved recipient name] line with the channel contact detail, omitting the “1 recipient” count. A child’s profile remains the context, but the account manager is the actual recipient; missing contact details must be explicit, never invented.

- Student/family Send SMS and Send email actions open their conversation screens directly. Hide profile tabs and the contact action bar while messaging. Do not add a Communication profile tab, a channel switcher, or an Open communication workspace action.
- During student/account messaging, put a single icon-only Back chevron immediately before the avatar in the profile header. Use the accessible label Back to profile without a tooltip or visible label; do not render a redundant content Back row. Restore the originating section and retain drafts. Email drafting likewise puts its icon-only Back to email conversation action in its header. Direct-open profiles must not reserve an empty Back slot.
- Conversation surfaces fill the remaining panel height; scroll history inside the surface and keep the SMS composer below it. At wide container sizes, SMS conversation and phone-preview columns split 50/50; narrow containers prioritize the conversation. Email’s New email/Continue draft action belongs at the toolbar’s top-right, not in the thread list. Email reading stays compact; drafting uses a focused workspace. Do not render the local-preview disclaimer in these surfaces; actual sending remains disabled.
- Important student-tab actions use medium Button sizing, including Add note, Create statement, Issue invoice and Add subscription.

- Messaging screens share a content toolbar: 6px top inset, existing 24px desktop / 16px mobile gutters, 44px minimum navigation target, and 14px separation before the conversation. Use the shared BackControl (icon-only in profile and email-drafting headers): neutral text, no underline, no hover treatment, and no tooltip (including on focus). Preserve an explicit neutral keyboard focus ring and accessible destination labels. Apply this same appearance to all BackControl usages, whether labeled or icon-only, and do not add page-specific Back styles. Apply the same toolbar spacing to email drafting. Keep readable timestamps and message-preview contrast; do not use pale metadata text on these surfaces.

- Chat timestamps use A moment ago (under one minute), Today, Yesterday, or an exact date with year; times use two-digit 12-hour hours/minutes and AM/PM, without seconds. Sam Kim’s preview phone is the fictional (202) 555-0142; preserve explicit missing-contact fallbacks for other fixtures.

- Student section headers use the shared SectionHeader row with a 44px minimum, zero heading margins, and the panel content gutter. Cancellation stays inline below existing navigation, retaining profile identity and tabs. Invoice metadata uses a compact label/value list; optional custom fields and free-text notes belong to the invoice and its exports.

- V3 student preview (`prototype=v3`) uses a single wider profile panel, capped at 1160px, with all workspace tasks inline below persistent profile navigation. Task shells omit duplicate profile headers; calendar columns respond to panel width and keep horizontal scrolling inside the grid. V1/V2 presentation remains unchanged.
- V3 Upcoming lessons uses List/Calendar toggles, shared week state, and identical Move/Cancel actions on cards and calendar blocks. Omit instructional calendar cards. Moving a lesson shows violet booked/original blocks, pale-blue dashed availability and a blue selected replacement, with text labels and a legend; omit the original-lesson summary card. Makeup booking stays in the Makeups tab and returns to its bin.
- V3 screen headers must use SectionHeader, not hand-built header rows. Start titles at the shared content edge without an empty navigation column; place V3 Back immediately before task titles, with no empty slot on root sections. Makeup-bin student names use the same header structure. Actions wrap below the title on narrow containers. The panel owns scroll reset on screen transitions; task headings must not scroll away the content's top padding. Browser coverage compares actual header/title coordinates across list, calendar, move, makeup, billing, invoice, notes, subscription and cancellation.

- Shared time-grid calendars use 52px day headers and one inherited 30px quarter-hour token for axis, rows and gridlines; week/teacher toolbar gaps are 8–10px. Keep 44px navigation/filter targets. Rescheduling omits the original-lesson subtitle; the original remains labeled in the grid.

- Shared calendar weeks always include Saturday (Monday–Saturday by default); retain Sunday when existing lessons require it. Availability uses pale blue with dashed borders; selected replacements use stronger blue with a solid border.

- Billing uses one neutral total due, with due dates/statuses on invoice cards rather than a split balance summary. Total Pay and non-overdue invoice Pay actions use neutral secondary buttons; overdue invoice Pay actions are red on both cards and documents. All use matching 166px width and shared medium sizing; include the amount in Pay labels. Invoice metadata editing is labeled Customize invoice fields.

- Email communication places Messaging recipient details and New email on one shared toolbar row. Reader metadata has separate From/To rows and a gap before the body. Replies compose inline below the selected thread, with per-thread drafts separate from the full-workspace New email draft.

- Saved payment methods distinguish Name on card from Save card for (the billing payer). A different cardholder name must not add family members, payers or portal access, or alter invoice responsibility. Preview card entry uses masked sample cards only and requires confirmation of authorized use. Payment methods belongs to the account holder, not the student. Student billing allows individual invoice payments through a modal that identifies the student, payer and eligible saved cards. Do not show payment-method management, combined Pay, billing management, or a permanent account-handoff message on child billing. Payment methods is a secondary button in the account-holder billing header. A missing saved card explains that methods are managed on the payer’s account; only offer account navigation when that payer has a supported account route. Payment methods returns only to that holder’s billing.
